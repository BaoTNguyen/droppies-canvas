# Color Palette System

## What It Does
Manages named color palettes for the brush. One built-in default palette ships with the app. Users can create custom palettes, edit their colors, duplicate existing palettes, and delete custom ones. The last-used palette and color are remembered between sessions. Changing the active color also recolors any currently-selected strokes.

## How to Use It
- Click the **color swatch button** in the toolbar (shows current color as hex code) to open the color picker panel
- Click any color swatch in the picker to set it as the active brush color
- Use the **palette dropdown** to switch between palettes
- Click **New Palette** to create a custom palette (prompts for a name)
- Click **Edit Palette** to add/remove/reorder colors within the active palette
- Click **Delete Palette** to remove a custom palette (built-in palette cannot be deleted)
- Palettes support 1 to 40 colors each (`Config.MIN_PALETTE_SIZE` / `Config.MAX_PALETTE_SIZE`)

## Architecture Notes
`PaletteManager` is an autoloaded `Node`. On startup it loads the built-in palette from `default_palette.tres` (a Godot resource), then reads `user://palettes.cfg` (a `ConfigFile`) for any user-created palettes. Each custom palette has a 32-character UUID generated by `Utils.generate_uuid()`. Palettes are sorted alphabetically by name (with a custom `PaletteSorter`), except the built-in one loads first.

The last-used palette UUID is persisted in `user://settings.cfg` under `color_palette_uuid_last_used`. On startup, `PaletteManager` restores the active palette by UUID lookup.

The built-in palette is marked `builtin = true` and cannot be deleted. Custom palettes are stored as INI sections in `user://palettes.cfg` with their UUID as the section key.

Color changes flow: `ColorPalettePicker` → `Main._on_BrushColorPicker_color_changed` → `_toolbar.set_brush_color` + `_canvas.set_brush_color`. If a stroke is selected, `SelectionTool._on_brush_color_changed` intercepts the color change and recolors selected strokes immediately.

## Pros
- UUID-based palette identification is robust: renaming a palette does not break the "last used" restore on next launch
- The 32-char random UUID avoids collisions between user palettes even without a central registry
- Palette creation, duplication, editing, and deletion are all handled with dedicated dialogs — the UX is complete
- The color button in the toolbar shows the active color as a hex code with auto-contrasting text (black on light colors, white on dark) — a nice detail

## Cons / Limitations
- **No per-stroke custom color** outside of palettes: users cannot type an arbitrary hex value into the toolbar directly; they must edit a palette to add the color first
- **No color picker with HSL/HSV sliders** in the main workflow: the `ColorPicker` node is used only for the canvas background color; brush color is palette-only
- The `duplicate_palette` method has a `TODO` comment noting colors may be passed by reference rather than value — if the original palette colors are mutated after duplication, the duplicate's colors may be corrupted
- Palette sort is alphabetical only; there is no drag-to-reorder
- Max 40 colors per palette is a hard cap with no explanation exposed to users

## Decision Guidance
The palette system is functional and well-structured for a focused drawing tool. The biggest practical limitation is the absence of a free-form color picker for the brush — requiring a palette edit to use an arbitrary color is friction. Adding a "custom color" slot or a free-form picker popup would significantly improve workflow for users who reference specific brand or annotation colors.
